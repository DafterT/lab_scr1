### Вектор прерываний, ресетов и настройка линковщика
После успешной сборки проекта необходимо выполнить модификацию в соответствии с заданием.  
Начать стоит с SCR1_ARCH_RST_VECTOR и SCR1_ARCH_MTVEC_BASE которые задаются в `src\includes\scr1_arch_description.svh`  
Эти параметры отвечают за следующие функции:
 - `SCR1_ARCH_RST_VECTOR` - адрес первой инструкции, с которой процессор начинает выполнение после сброса (reset vector). По умолчанию `0x200` — это «точка входа» программы после включения/перезагрузки ядра.
 - `SCR1_ARCH_MTVEC_BASE` - базовый адрес обработчика исключений и прерываний, который записывается в CSR-регистр mtvec при reset. По умолчанию `0x1C0` — это адрес, куда процессор будет переходить при возникновении trap или interrupt.  

Выполним модификацию и зададим им значения в соответствии с вариантом:
```svh
parameter bit [`SCR1_XLEN-1:0] SCR1_ARCH_RST_VECTOR = 'h200;
parameter bit [`SCR1_XLEN-1:0] SCR1_ARCH_MTVEC_BASE = 'h400;
```
Теперь нужно обновить линковщик для корректного размещения обработчика trap и стартового кода по адресам, которые заданы в параметрах ядра. Для этого в скрипте линковки явно указываются новые базовые адреса: секция `.text.init` (trap_vector) должна начинаться с адреса, равного MTVEC_BASE, а секция `.text.start` — с адреса, равного RST_VECTOR. Такой подход гарантирует, что при возникновении исключения или после сброса ядро всегда перейдёт к нужному коду.

Изменения в файле `sim/tests/common/link.ld`  
Заменим строку:
```ld
. = 0x100;
PROVIDE(__TEXT_START__ = .);
*(.text.init)
```
На:
```
. = 0x400;
PROVIDE(__TEXT_START__ = .);
*(.text.init)
```
Теперь секция `.text.init`, содержащая код `trap_vector`, будет размещена начиная с адреса `0x400`, что соответствует значению `SCR1_ARCH_MTVEC_BASE = 'h0400`. Теперь ядро при возникновении исключения перейдёт точно по адресу 0x500, где будет лежать наш обработчик.

Также добавим новую секцию после блока `.text.init`:
```
.text.start 0x200 : {
   PROVIDE(__TEXT_END__ = .);
   PROVIDE(__TEXT_START__ = .);
   *(.text.start)
} >RAM
```
Это создаст отдельную секцию `.text.start` с базовым адресом `0x200`, что соответствует значению `SCR1_ARCH_RST_VECTOR = 'h200`. До этого `_start` размещался в общей секции `.text` неявно, теперь точка входа программы гарантированно будет лежать по адресу `0x200`, откуда ядро начнёт выполнение после сброса.  
Поместим код в секцию `.text.start`, для этого в файл `sim\tests\common\riscv_macros.h` перед `_start:` добавим обозначение секции:
```h
_report:
        j sc_exit;
        .balign  64;
        .globl _start;
        .section .text.start;
_start:   
        ...
```
Таким образом мы изменили адреса trap вектора и адреса ресета. Выполним сборку:
```bash
make clean
make TARGETS="riscv_isa"
```
В результате получаем следующую ошибку:
```

```
Здесь написано, что секция .text.start накладывается на секцию .text.init. 
Попробуем исправить это и обновим линковщик, явно задав место в памяти для trap vector:

  .text.head 0 : {

### Обновление обработчика исключений
К этому моменту отчета имеем настроенный линкер, осталось лишь обработать ошибку Instruction address misaligned.  
Instruction address misaligned - исключение, которое возникает при выполнении команды перехода (`j`, `jal`), если целевой адрес не выровнен должным образом. Адреса инструкций должны быть выровнены либо по 2 байта (кратны 2), либо по 4 байта (кратны 4). Выравнивание по 2 байта применяется исключительно при использовании расширения `C` для сжатых (compressed) инструкций, которые занимают 2 байта.  
Первым делом создадим текст, который будет выводится при возникновении ошибки:
```h
#define RVTEST_CODE_BEGIN
        MSG_TRAP:
          .string "misalign trap";
        .section .text.init;
```
Далее необходимо выводить данный текст при возникновении ошибки, для этого модифицируем код для `trap_vector`:
```h
trap_vector:
        /* init for loop, 0xf0000000 address for print */
        lui a6, 0xf0000; 
        la a7, MSG_TRAP; 
next_iter:   
        lb a5, 0(a7); 
        beq a5, x0, break_from_loop;
        sw a5, 0(a6);   /* write to a6 char for print */
        addi a7, a7, 1;
        jal x0,next_iter;
break_from_loop:     
        ...
```
Этот код проходит по всей строке и последовательно выводит каждый её символ.  
Обновим файл `sim\tests\riscv_isa\rv32_tests.inc` и зададим в качестве тестов только тот, который соответствует заданию:
```
rv32_isa_tests += isa/rv32mi/ma_fetch.S
```
Остальные тесты были удалены

## Вывод
В ходе лабораторной работы ядро SCR1 было адаптировано под индивидуальный вариант: настроены reset и trap векторы, реализована обработка исключения Instruction address misaligned и организован вывод строки "misalign trap через побайтовую запись в область памяти вывода по адресу `0xf0000000`. Reset vector закреплён за адресом `0x200`, а trap vector за `0x400`, при этом значения согласованы как в параметрах `SCR1_ARCH_RST_VECTOR` и `SCR1_ARCH_MTVEC_BASE`, так и в linker script, что обеспечивает корректный старт и переход к обработчику исключений строго по заданной схеме.​  
В итоге цель лабораторной работы достигнута: конфигурация ядра и линковки соответствует варианту, обработчик исключения Instruction address misaligned корректно отрабатывает и выводит требуемое сообщение, а симуляционная среда на базе SCR1 может использоваться как основа для дальнейших экспериментов с системой прерываний и обработкой исключений в архитектуре RISC-V.​  
В ходе лабораторной работы были получены практические навыки ручной настройки карты памяти и привязки программного кода к конкретным аппаратным адресам с использованием линкер-скриптов, а также конфигурирования параметров ядра SCR1, определяющих reset и trap векторы. Такой опыт позволяет на практике увидеть, как выбор адресов для секций и обработчиков исключений напрямую влияет на поведение системы при сбросе и возникновении исключений, и подчёркивает, что в встраиваемых системах разработчик несёт ответственность за явное описание размещения кода и данных в памяти устройства.
